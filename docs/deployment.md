# Развёртывание и эксплуатация — инструкция для ИТ-отдела

Этап 13 (стабилизация Вехи 1). Дополняет раздел «Развёртывание на боевом Linux-сервере» в
`README.md` — здесь собраны справочник переменных окружения, процедура резервного копирования,
обновление версии и типовые операции, которых в README не было. Актуально для Вехи 1
(один сервер, HTTP, без multi-instance-нагрузки); HTTPS/TLS и реальная многопользовательская
нагрузка на боевом Linux — Веха 2 (не проверялось на этом окружении, см. `SESSION_LOG.md`).

## Состав системы

- `server/` — Node.js/Express API + PostgreSQL через Prisma. Порт по умолчанию 4000.
- `client/` — React SPA, собирается в статику (`client/dist/`), раздаётся тем же nginx, что
  проксирует `/api/` на сервер.
- `server/uploads/chart-images/` — единственное постоянное файловое хранилище приложения
  (загруженные картинки графиков, Этап 7). PDF **не** сохраняются на диск — генерируются по
  запросу через headless Chromium (Playwright) и отдаются сразу в ответе (Этап 6).

## Версии зависимостей

- Node.js LTS 18+ (разработка и проверка велись на 24.x).
- PostgreSQL — разработка и проверка велись на 17.
- `playwright@1.61.1` — версия запакована в `package.json`, привязана к закэшированному Chromium;
  при обновлении playwright пересмотрите, нужен ли повторный `npx playwright install chromium`.

## Справочник переменных окружения (`server/.env`)

| Переменная | Назначение | Замечания |
|---|---|---|
| `DATABASE_URL` | Строка подключения PostgreSQL | `postgresql://user:password@host:5432/db` |
| `JWT_SECRET` | Секрет подписи JWT-токена сессии | Длинная случайная строка (`openssl rand -base64 48`). **Смена секрета мгновенно инвалидирует все активные сессии** — все пользователи будут разлогинены. Планируйте смену вне рабочего времени и предупреждайте пользователей. |
| `PORT` | Порт Express-сервера | По умолчанию 4000 |
| `NODE_ENV` | `production` в проде | Влияет на поведение Express (детализация ошибок и т.п.) |
| `CLIENT_ORIGIN` | **Двойная роль.** (1) Источник для CORS — запросы браузера с этого origin разрешены. (2) Адрес, по которому серверный процесс через headless Chromium сам обращается к собранному клиенту для рендера PDF (Этап 6, `server/src/routes/presentationExport.ts`). | На боевом сервере это почти наверняка **не** публичный домен, а адрес, реально доступный с той же машины, где крутится Node-процесс (например, `http://127.0.0.1`) — нужно, чтобы и браузер пользователя, и локальный Chromium одинаково понимали этот origin, либо разносить два разных механизма. Не проверено end-to-end на боевом Linux — часть Вехи 2. |
| `SEED_ADMIN_LOGIN` / `SEED_ADMIN_PASSWORD` | Используются только скриптом `npm run seed` при первом запуске, создают первого администратора | Смените пароль сразу после первого входа (кнопка сброса пароля в UI администрирования, Этап 12) |

**Не вынесено в `.env` (зашито в код — смена требует правки кода и пересборки):**
- Время жизни сессии — `COOKIE_MAX_AGE_MS` в `server/src/routes/auth.ts`, сейчас 10 часов.
- Порог «дедлайн приближается» для автоматических уведомлений — `DEADLINE_APPROACHING_HOURS` в
  `server/src/utils/notifications.ts`, сейчас 24 часа.

## Установка «с нуля»

```bash
cd server
npm ci
npx playwright install chromium
npx playwright install-deps chromium   # системные библиотеки, нужно на «голом» Linux
npm run build
npx prisma migrate deploy               # НЕ migrate dev — deploy не создаёт новых миграций, только применяет существующие
npm run seed                            # один раз, создаёт первого администратора из .env
```

```bash
cd client
npm ci
npm run build                           # результат в client/dist/, его раздаёт nginx
```

Затем — systemd-юнит (`deploy/weekly-report-api.service`) и nginx (`deploy/nginx.conf.example`),
как описано в `README.md`.

Эта последовательность проверена в Этапе 13 на пустой локальной PostgreSQL (миграции + seed) —
полный прогон на боевом Linux (systemd+nginx целиком) остаётся Вехой 2.

## Обновление версии (деплой нового кода)

```bash
git pull
cd server && npm ci && npm run build && npx prisma migrate deploy
cd ../client && npm ci && npm run build
sudo systemctl restart weekly-report-api
```

nginx перезапускать не нужно, если конфиг не менялся — он раздаёт статику `client/dist/`
напрямую с диска.

## Резервное копирование и восстановление

НФТ SRS §4.3 требует бэкап не реже раза в сутки. В каркасе это не автоматизировано — настройте
cron на боевом сервере:

```bash
# /etc/cron.d/weekly-report-backup — ежедневно в 03:00
0 3 * * * postgres pg_dump -Fc weekly_report > /var/backups/weekly-report/db-$(date +\%Y\%m\%d).dump
```

Храните также `server/uploads/chart-images/` — картинки не входят в дамп БД:

```bash
0 3 * * * root tar czf /var/backups/weekly-report/uploads-$(date +\%Y\%m\%d).tar.gz -C /opt/weekly-report/server uploads
```

Восстановление:

```bash
# БД
pg_restore -d weekly_report --clean --if-exists /var/backups/weekly-report/db-YYYYMMDD.dump

# Загруженные картинки
tar xzf /var/backups/weekly-report/uploads-YYYYMMDD.tar.gz -C /opt/weekly-report/server
```

Ротацию старых бэкапов (сколько хранить) согласуйте с ИТ-отделом отдельно — SRS этого не
регламентирует.

## Управление местом на диске

- `server/uploads/chart-images/` растёт по мере наполнения циклов картинками графиков; при замене
  или удалении картинки старый файл физически удаляется (Этап 7), но накопление по мере роста
  числа недель — ожидаемо. Мониторьте занятое место, включите в бэкап (см. выше).
- Кэш Chromium от Playwright (`~/.cache/ms-playwright`, от пользователя, под которым запущен
  сервис) — сотни МБ, разово при установке.
- PDF-файлы **не** накапливаются на диске — генерируются по запросу и не сохраняются.

## Логи и мониторинг

- `GET /api/health` — эндпоинт проверки живости (`{"ok":true}`), используйте для healthcheck.
- Логи процесса — через systemd journal: `journalctl -u weekly-report-api -f`. Отдельного файла
  логов сервер не ведёт (`console.log`/`console.error` → journal).
- Необработанные исключения в async-роутах ловятся глобальным обработчиком
  (`process.on("unhandledRejection")` в `server/src/index.ts`) и только логируются — не роняют
  процесс, но и не отвечают клиенту (запрос, скорее всего, повиснет до таймаута на его стороне).

## Известные ограничения пилота (Веха 1)

Зафиксировано осознанно при сдаче Этапа 13, не является дефектом — см. `REQUIREMENTS.md`, Этап 13,
раздел E, для полного списка и обоснования каждого пункта:

- Удаление отдела, который был для шаблона единственным назначением, каскадно делает шаблон видимым
  всем спикерам (правило «0 назначений = общий» применяется и здесь).
- Кроме подтверждения на жёсткое удаление пользователя, в приложении нет других confirm-диалогов —
  архивация, разборка презентации, удаление отдела/поля/блока шаблона срабатывают сразу по клику.
- Легаси-шаблону (с уже существующими слайдами) по-прежнему можно добавить новое поле задним числом.
- Сборка презентации и подстановка заглушки для несданного слайда — ручные действия администратора,
  не «одной кнопкой» (согласованное отклонение от буквальной формулировки SRS FR-ASM-01/02).
- Реальная email-рассылка приглашений, HTTPS/TLS, интеграция с AD/LDAP — вне Вехи 1, см. Веху 2.
