# Еженедельный свод SIGIR: самообслуживаемая форма вместо pptx+почты

Перенесено из `maxbot` 04.10.2026 — см. `SESSION_LOG.md`, запись от этой же даты, за
обоснование решения не продолжать `client/`/`server/` этого репозитория.

## Контекст

Сейчас: 16 руководителей отделов правят свои мини-шаблоны в `.pptx`, присылают по почте
пользователю, тот вручную собирает в один файл и отдаёт Клоду; Клод конвертирует через
`markitdown` и вручную переносит цифры в HTML-артефакт «Свод недели SIGIR» (ledger-дизайн,
живой URL `https://claude.ai/artifact/8wMDdmHwTafFSkYrRTjj4p`). Узкое место — три ручных
шага (редактирование → почта → сборка), и то, что ассистент не видит первоисточник, только
агрегированный файл.

Решение — не чинить это через `sigir1`-сервер (см. README/SESSION_LOG — застрял на хостинге
и дизайне), а построить как Claude Artifact: без своего сервера/БД/деплоя, с переиспользованием
уже одобренного ledger-дизайна для чтения, и generic-движком блоков для записи.

## Архитектура

### Capabilities
`capabilities: {db: {}, user: {}}`.

### Модель данных (`db`)
- `departments` — 16 документов, стабильны между неделями: `{id, name, role, group,
  navLabel, order, ownerUserIds: [...], template: [...]}`. `template` — дерево блоков
  отдела (тот же формат, что в Этапе 1, см. `app.html`): `row2`/`cols3`/`subcard`/`block`
  как контейнеры, `table`/`bullets`/`meterRow`/`statRow`/`kv`/`taglist`/`segments`/
  `subgroup`/`text`/`risk`/`raw` как листья. У каждого листа — стабильный `id` для адресации
  записи.
- `weeks/<weekId>` — один документ: `{weekNumber, periodLabel, meetingLabel, deptCount}`.
- `weeks/<weekId>/departments/<deptId>` — то, что реально меняется каждую неделю:
  `{status: "reported"|"no_report", values: {<leafId>: <value>, ...}, footer: {...}}`.
  По умолчанию `no_report` — рендерится как плашка-заглушка, пока кто-то не заполнит раздел.

### Права на запись — доверие без барьера (подтверждено пользователем)
Дефолтное поведение `db` УЖЕ подходит без кастомных `rules`: «Contributors (interact) и выше
перезаписывают/удаляют» — то есть любой приглашённый соавтор технически может писать в любой
документ. Мягкая маршрутизация вместо барьера: кнопка «Это мой раздел» пишет
`user.id()` в `departments/<deptId>.ownerUserIds`; у «своих» разделов кнопка редактирования
заметнее, но у любого соавтора она есть everywhere.

**Приглашение соавторов — ручной шаг пользователя** (через Share-панель артефакта), ассистент
не может пригласить людей программно.

### Единый артефакт, два режима
Один и тот же артефакт: по умолчанию — ledger-рендер из `db` (тот же CSS, что у живого
свода); на каждом разделе — иконка редактирования, видимая вошедшим соавторам
(`user.canEdit()`). Клик открывает простую форму для листьев этого раздела, сохранение —
`db.update()`.

## Этапы

**Этап 1 — ГОТОВО (04.10.2026).** Рендер из данных (без прав на запись), 16 отделов,
~12 типов блоков, проверено живьём побайтово против живого свода. Тестовый артефакт:
`https://claude.ai/artifact/LD3xCqmtEKQftWbM38WzB9`.

**Этап 2 — в работе.** `db`/`user` capabilities, чтение всех 16 отделов из `db` (вместо
инлайн-JS), редакторы для пилотных 1-2 отделов (простая плоская форма, не универсальный
движок под все 16 сразу — это Этап 3), самоназначение владельца. Пилот — реальная неделя,
2-3 знакомых руководителя параллельно с обычной pptx-отправкой (двойная подстраховка).

**Этап 3 — полный раскат.** Универсальные редакторы под все типы блоков/все 16 отделов,
приглашение оставшихся руководителей, остановка сбора pptx по почте.

## Риски (сознательно принятые)

- Любой соавтор технически может отредактировать чужой раздел — страхуемся UI-подсказкой,
  не правами.
- Нужен Claude-аккаунт у каждого руководителя отдела + разовое приглашение пользователем.
- Графики (Подрядчики, line-chart) остаются ручной правкой — не часть формы, `raw`-блок.
- Нет формального воркфлоу «на проверке/принято» — сохранение сразу публикует.
